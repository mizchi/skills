AI 臭さを数値にしたくて一晩やってみたら、指標のほうは動いたのに、その指標が自分で書いた偽物を見抜けないことがわかったので、その話を書きます。

## 材料

人間の日本語として zenn の自分の記事 18 本を使った。コードブロックを除いた散文で 937 文 / 64,340 文字になる。

先に断っておくと、これは「人間の文章」の分布ではなく**著者 1 人の文章**の分布である。以下に出てくる「人間側」の band は全部そう読んでほしい。他人の文体に当てるには、その人のコーパスで band を引き直す必要がある。

人間の英語としては、エンジニアリング指標についての技術記事 1 本 (1,813 語) を選んだ。

比較対象は、未編集の LLM 出力を模した合成サンプル 3 本。

3 本目は自分で書いた模写なので、以下に出てくる「AI 側」の数字は全部、自分がモデルの癖を真似た文章の測定値でもあるという点は先に書いておく。

## 作ったもの

既存研究には表層シグナルの閾値が一通り出回っているので、文長の変動係数・語彙の多様性・特定フレーズの出現率あたりを全部実装して `slopscore.py` という lint にまとめた。stdlib だけで動いて API は要らない。

```bash
python3 slopscore.py draft.md            # md / html、コードブロックは除外
python3 slopscore.py --lang ja draft.md
python3 slopscore.py --baseline corpus/*  # コーパスの分布を出す
```

1 文書につき 8 個のシグナルを測って予算を超えた個数を件数として報告し、床を超えると exit 1 を返すので CI にもそのまま置ける。

結果は素直だった。

```
日本語   人間 18 本 = 0〜1 件   AI = 7 件
英語     人間        = 0 件      AI = 8 件
```

どちらの言語でもきれいに分かれたので、この時点では素朴に使えると思っていた。

## 洗浄版

問題に気づいたのはそのあとで、AI サンプルに対して **lint が出した指摘だけ** を機械的に潰した版を作ってみたときだった。

語句を置換して進行実況の文を削除しただけで、主張も具体例も数値も一行として足していない。

```
ai_ja.md              CV 0.32   7 tells    ← 未編集
ai_ja_laundered.md    CV 0.38   0 tells    ← 中身は同じ。洗浄済み
jev-is-gpu-for-llms   CV 0.57   1 tell     ← 自分が実際に書いた記事
```

洗浄版が 0 件になった。中身を一行も足していないのに、本物の記事 18 本のうち 5 本に勝って残り 13 本と同点、という点数が出てしまった。

## 洗浄版に残っていたもの

置換の作業は本当に機械的で、「〜することができます」を「〜できる」に縮め、「型安全性を確保することは非常に重要です」のような主語のない当為の文を消し、「前節では any 型について述べました。本節では型推論について説明します」を落とし、末尾の「参考になれば幸いです」を削っただけである。

これで lint の 8 シグナルが全部 ok になった。変動係数が 0.32 から 0.38 に上がったのも、文が短くなってばらつきが相対的に増えただけで、書き方が変わったからではない。

残ったのは、たとえばこういう段落だった。

> 型安全性はチーム開発でも効きます。型情報がドキュメントとして働くので、新しいメンバーがコードベースを読みやすくなります。

書いてあることは正しいし、日本語としても読みやすい。ただ、どのプロジェクトの話でもなく、誰がいつ測ったのでもなく、段落ごと削除しても文書から失われる事実がゼロなので、この段落を読んだ人間が持って帰れるものは一つもない。

そして lint はこれを検出できない。判定の根拠にできるシグナルが、一つも立っていないからだ。

自分はこれを、表層シグナルというのが結局 **find-and-replace で消える** 側の性質しか見ていなかった、という話だと思っている。

消せるものは、消されたら見えなくなる。

言われてみれば当たり前なのだけど、反例を手で作るまでは「語句は消えても文長分布や語彙の偏りみたいな統計のほうは残るだろう」と何となく思っていた。

残らなかった。

## 死んだシグナル 3 つ

[jev-playground](https://github.com/mizchi/jev-playground) の実測ノートに、閾値をいじる前に **gap を見ろ** という規則がある。

判定を score 順に並べて当たりと外れの間にどれだけ差があるかを先に測り、差が広ければ閾値はどこに置いても同じ答えになるし、差が狭ければそれは閾値の問題ではなく質問そのものが間違っている、という切り分けである。

手持ちのシグナルに片っ端から当てたら、3 つ落ちた。

**日本語の文長 CV は使えなかった。**

人間側の下限 0.36 に対して AI が 0.32 なので差は +0.04 しかなく、同じ指標を英語で測ると 0.62 対 0.24 で +0.38 つくから、言語をまたいだ瞬間に死んでいることになる。日本語は体言止めや短い断片で文長が勝手にばらけるぶん、人間側のレンジが上にも下にも広がってしまうのだろう。

CV の床を 1 本だけ引いて両言語に流用している実装は、どちらかの言語で当て推量をやっている。

**体言止めと反問は、無いことを根拠にできなかった。**

どちらも人間の記事に出てくる装置で AI サンプルは両方ゼロだったので使えそうに見えたのだが、人間側 18 本を数えたら 3 本がどちらもゼロで、人間側の下限自体がゼロだった。あることは加点になるが、無いことは何の証拠にもならない。

この非対称を踏み抜くのが自作検出器で一番よくあるバグだと知っていて、それでもまさか自分がその場で踏むとは思っていなかった。

**語彙の多様性は符号が逆だった。**

「AI は語彙が狭い」という通説は疑わずに実装したのだけど、英語で測ったら AI サンプルのほうが高かった (MATTR 0.84 対 人間 0.80)。人間は `commit count` を最後まで `commit count` と書き続けるもので、用語を揺らさないのが技術文書として正しい作法だからそうなるのであって、モデルのほうは律儀に同義語を探しに行く。

まあ、言われてみればそのとおりではある。

素の type-token ratio のほうは、同じ英文で TTR 0.418 / MATTR(100) 0.801 という値が出るうえ、TTR は文書が長いほど下がるので長さの違う文書を比較できず、指標としてそもそも成立していなかった。

## 英語側で壊れていた閾値

三つ組の並列 (tricolon) には「200 語に 1 個を超えたら機械的」という閾値が出回っているのだが、人間の参照記事を測ったら 1.55、閾値の 1.55 倍だった。人間が書いた記事なのだから、これは閾値のほうを疑うことになる。

引っかかった 14 件を手で分類した。

```
実在する列挙 (問題なし)      12 件   LOC, commit count and PR count
                                 Microsoft, Accenture and a Fortune 100 company
そもそも三つ組でない (誤parse)  1 件   if your platform is weak, AI makes it weaker
                                 faster, and activity metrics will ...
抽象の三つ組 (これが AI 臭)     1 件   verification, systems thinking, and accountability
```

指せるものが 3 つ並んでいるのは、ただの列挙である。指せない抽象が韻を踏んで 3 つ並んでいるほうが tell なのだけど、狙っていたその形は 14 件のうち 1 件しかなかった。

残り 13 件は誤検出で、しかもそのうち 1 件は閾値のせいではなく、コンマで区切られた節を自分の正規表現が三つ組と読み違えただけだった。

誤検出率 93%。

判別しているのは **数ではなく具体性** で、これは正規表現の仕事ではない。

em ダッシュも測っておいたが、人間 0.0 / 1000 語に対して AI も 0.0 / 1000 語で、一番よく引用される tell がこの標本では一番情報を持っていなかった。

## 生き残った 1 本

では、消せない性質なんてあるのだろうか。語句も統計も洗い流せることが分かってしまったので、最初はもう打ち手がない気がしていた。

一番効いたのは、k16shikano さんの [日本語ライティング規範](https://gist.github.com/k16shikano/eb2929f13ed19c97188393d297be8432) に置かれている判定軸だった。

> **その文が更新するのは「状況」か、「文書」か。**

状況を更新する文は、対象世界の出来事・データ・発言、あるいは語り手の判断状態 (思い込み、保留、後悔、譲歩) を新しく伝えている。文書を更新する文は、この章がどう見えるか・次に何を書くかだけを伝えていて、原則として削除する。

これが強いのは、世に出回っている AI 臭チェックリストの大半を 1 本の軸が吸収してしまうところだ。進行実況、空虚な前置き、対称的な見出し、内容のない要約と並べてみると、どれも「文書を更新する文」の一種でしかない。

そのうえで、文書について語る文を状況について語る文に書き換えるには状況の側に書くべき中身を持っている必要があるので、この軸は find-and-replace では通過できない。

さっきの洗浄版に残っていた段落も、この軸にかけると即死する。「型情報がドキュメントとして働く」は一般論であって、この文書が扱っている状況を何も更新していない。

状況側に直すにはどのプロジェクトで何人が何日で読めるようになったのかを書くしかなくて、そこで書き手は測るか諦めるかを選ばされることになる。

一方で規範の側には数字が一つもなく、「拍を作れ」と書かれていても目標値がないので、そこは実測で埋めた。文長の十分位 (16 / 23 / 29 / 35 / 41 / 47 / 54 / 63 / 79 文字)、短文 (15 字以下) の比率 8%、長文 (70 字以上) の比率 14%。

## 2 層に分けた

| | 表層 | 判断層 |
| --- | --- | --- |
| 見るもの | 語句と形 | 文が情報を運んでいるか |
| コスト | 無料・決定的 | 1 文書 1 リクエスト |
| 未編集 AI との差 | 広い (日本語 0〜1 対 7 / 英語 0 対 8) | +0.53 |
| **編集済み AI との差** | **ゼロ** | **+0.21 (狭い)** |
| find-and-replace で消える | 全部消える | 消えない |
| 使い方 | 床付きの lint | 指数にしたいが、まだ足りない |

表層は無料だし未編集の出力は本当に引っかかるので、slop 用のスペルチェッカーとして走らせる価値はある。ただし指数にはできない。

判断層に要るのは、0〜2 のスコアと真偽を JSON で返せることだけである。専用のモデルでなくてよく、キーがなければ同じ質問文をルーブリックとして普通のモデルに流しても機能する。

自分が使ったのは Jev — 文字列ではなく型付きの確率判断を返すモデル — で、閾値を引ける校正済みの確率が返るところだけが違う。質問の設計そのものは移植できるので、以下は API を問わない話として読んでほしい。

設計規則は実測ノートに全部書いてあるので、表で済ませる。分母は元実験のラベル付き件数で、**24 はシェルコマンド 24 件**（allow / confirm / block のラベル付き）、**36 は 8 指標の自クラス判定 36 件**。

| 規則 | 守らないと |
| --- | --- |
| 順序のある結論は `score`、`choice` で聞かない | シェル 24 件で 19/24 止まり。`score` にすると 23/24 |
| 閾値は質問ごとに引く | 自クラス判定 36 件で、共通 1 本なら 13/36、個別なら 24/36（誤検出は同じ） |
| 「該当なし」は選択肢ではなく別の問い | `choice` は必ず選ぶので範囲外が自信のある誤答になる |
| 質問は全部 1 リクエストに詰める | 20 問で 246ms 対 5227ms、答えは 0.011 しか動かない |

この中で自分が一番間違えていたのは、表に入っていない方の規則だった。**段落を見ても決められないことを聞かない。**

「これは人間が書いたか」と直接聞けばいいのではないか、と最初は考えた。それは文章から検証できないので、聞くと自信のある無意味な数字が返ってくる。

実測ノートにも同じ形の失敗が載っていて、catch 節について「呼び出し元がこの失敗を知る必要があるか」を聞いたら 4 件の答えが全部真ん中に寄ったという例がある。catch 節を見ても決められないことを聞かれたモデルは、正しく「わからない」を返していたわけだ。

だから主質問は、段落だけ見れば答えられる形にした。

```json
{
  "document_updating": {
    "type": "score",
    "instructions": "この段落の文は、対象ではなく文書自身について述べている。",
    "criteria": [
      "すべての文が対象について述べている: 出来事、実測値、固有名、または書き手自身の判断 (思い込み、疑い、譲歩、後悔)",
      "混在: 対象について述べる文と、構成や扱う範囲を述べる文が混じっている",
      "ほとんどの文が文書自身について述べている: この節が何を扱うか、上で何を扱ったか、次に何が来るか"
    ]
  }
}
```

## 判断層で洗浄版を測った

表の「編集済み AI との差」に数字を入れないまま置いておくのは、この記事でやっている話と矛盾する。測った。

洗浄版・未編集 AI・本物の記事 (`jev-is-gpu-for-llms`) から段落を抜き、**出典を隠して混ぜて** 58 段落にし、`document_updating` を段落ごとに採点させた。採点者は出典を知らず、記事も読んでいない。

```
source          n   mean   du>=1   du=2   削除可
HUMAN          35   0.09      6%     3%      3%
AI_LAUNDERED   10   0.30     20%    10%     20%
AI_UNEDITED    13   0.62     38%    23%     31%

gap  HUMAN 対 AI_LAUNDERED  +0.21
gap  HUMAN 対 AI_UNEDITED   +0.53
```

順序は正しい。洗浄版は人間より高く出ているので、表層 lint が 0 件を返した文章を判断層は捕まえている。表層が人間より良い点を付けたのと対照すると、層を分けた意図は一応通っている。

**ただし +0.21 は、自分が冒頭で引いた規則だと「狭い」に入る。** gap 0.2〜0.3 は「答えがそもそも分かれていない、閾値ではなく質問を書き直せ」の帯である。自分の規則を自分の結果に当てると、この質問はまだ書き直しの側にある。

段落ごとに見ると理由がはっきりした。洗浄版 10 段落のうち 8 段落が du=0 で、採点理由は「型チェック無効化と絞り込み強制の機構」「型情報がドキュメントとして働く機構」だった。**機構を述べている文は、その機構が一般論であっても「対象について述べている」と読まれる。** 質問文が「文書自身について述べているか」しか聞いていないので、一般論と状況の区別は聞けていない。

つまり判断層は「進行実況」は捕まえるが、「正しい一般論で埋めた段落」はまだ捕まえられない。洗浄版で一番残っていたのがその形だったので、一番効いてほしいところで効いていない。

質問を「この段落の内容は、この文書が扱っている特定の事例からしか出てこないか」に書き直すのが次の手だと思うが、それは測り直してからでないと言えない。

報告は 3 つ並べて、1 つにまとめない。

```
removable tells:    0 / 8 signals over budget   (表層。指紋の有無で、中身の話ではない)
ai index:           0.58                        (判断層。driven by: document_updating 1.4)
unsupported claims: 2   L34, L71                (判断層。出典なしの断定。位置で返す)
```

層ごとに想定している敵が違うのに、まとめた数字を見せられた人間はそれを強いほうの数字だと思って受け取るので、まとめた時点で嘘になる。

## 外れていた自己認識

同じコーパスができたので、以前に書いた `mizchi-blog-style` という自分用の文体プロファイルも測り直した。

**「tl;dr 先出し。冒頭に 3〜5 箇条」と書いていた。**

数えたら 18 本中 17 本が冒頭に箇条書きを持っておらず、literal な `TL;DR` 見出しを使っているのは 1 本だけで、実際の冒頭は散文 1〜2 文の中央値 49 文字だった。

```
Jev を一晩叩いたので、その感想を書きます。タイトルは超大雑把な要約です。
前々から自作ブラウザを作ってみたかったんですよね。作ります。
人生で5度目ぐらいの Markdown Editor 実装をしました。今回が最速です。
速報気味。jev 同士に五目並べで対戦させて、速度を実測してみました。
(この記事の AI 成分は 5 割ぐらいです)
```

共通していたのは **機会があること** で、何かをやった、その報告として記事がある、という形になっている。「一晩叩いた」「人生で5度目」「速報気味」と、書いている理由が最初の一文に入っていた。

**「文末は〜と思う / 〜だろうが多い」と書いていた。**

3 つ合計で全文の 3.3% だった (と思う 1.2%、だろう 1.2%、はず・かも 1.0%)。文末の主流は敬体で、主観のほうは文末を濁すことではなく `自分` という語で出ていて、万字あたり 11.5 回、コーパス中で最強のマーカーだった。

**文体純度については何も書いていなかった。**

一番きれいに出た結果がこれで、18 本中 18 本が単一文体を 80% 以上の純度で保持しており、14 本は 100%、内訳は敬体 14 / 常体 4 / 混在 0 である。

ただし AI サンプルも 100% だったので、このシグナルは AI 検出には使えない。機械は文体を完璧に揃えてくるので、効くのは段落ごとに AI へ書き直させて継ぎ目で文体が割れる **編集済み** のときだろう。

あと `シュッと` は 64,340 文字で 3 回、万字あたり 0.5 回だった。多用するとパロディになるという注意は前から書いていたけれど、桁を知らなかったので実質的には守れていなかった。

## 一番効いたのは段落の粒度だった

ここまで全部マーカーの話で、それが失敗だった。上のプロファイルに合わせて記事を書いたら「っぽい」と言われたので、今度は談話レベルで測り直した。

```
                      mizchi 18本   未編集 AI   マーカー最適化した原稿
文 / 段落                    1.4         2.5              3.3
一文段落の割合                 64%         15%              13%
5 文以上の段落                  0%          0%              23%
冒頭段落の文数                 1〜2           3                3
見出しが名詞ラベル              84%           —              62%
コード間の散文 (文字)           102         396             1105
```

マーカーレートのほうは `自分` 11.1 対実測 11.5、文長 40 字対 43.6 と、全部目標圏に入れてあった。そのうえで段落の形は未編集 AI より遠く、粒度では AI のほうが正解に近かった。

一番効く成分はこれだった。

766 段落のうち 64% が一文で、5 文以上の段落は 18 本でゼロ件である。

Zenn のレンダリング都合ではないかを疑って連続する `<p>` の元行番号を調べたら、差が 1 すなわち単一改行のペアは 252 組中 0 組で、全部に空行が入っていた。

意図的な改行である。

しかも一文段落の平均は 48.8 字、18% は 70 字を超えていて、「一文で切るから短い」わけではまったくなかった。長い一文は **が / ので / のだが** で限定節を中に抱えている形で、自分は逆にその限定節を別の短文に割っていたから、段落を割ると同時に文まで短くしてしまっていた。

見出しも形が違っていて、149 / 178 = 84% が名詞句 (`作ったもの` `実装手順` `学び・苦労した点`)、問いが 9%、文が 7% だった。論評を見出しに書くのは英語圏のテックブログの形で、自分の記事の形ではなかった。

締めも外していた。

旧版のプロファイルには「`おわり` で足りる」と書いてあったのだが、18 本の最終段落を読み直したら `おわり` は 1 件もなく、支配的なのは次の行動・読者への誘い・未完の予告だった。

```
自分は次に、これを使って GitHub 以外で動く CI 環境を作っています。
もうちょっと練ったら後で紹介したい。
```

記事は完結せず、続いている作業を指して終わっている。自分の文体を自分で誤解していた部分が、マーカーより構造のほうに多かった。

## 信用してはいけないところ

AI 側のベースラインは冒頭に書いたとおり合成サンプル 3 本に乗っているので、差が存在すること自体は示せているが、差の幅は示せていない。ゲートとして運用に載せる前に、実物のラベル付きサンプルを足す必要がある。

英語の人間側は n=1 である。tricolon については 1 本の記事の中で誤検出が 13 件出ているので、標本が 1 でも閾値の設計が形から壊れていることは言い切れる。

ただし残りのシグナルについては、床をどこに引くかを詰めるだけの材料がない。

途中で数え間違いも 1 件出た。洗浄版との比較を最初「18 本のうち 6 本に勝った」と書いていたのだけど、これは日本語 CV の床を 0.45 から 0.35 に下げて advisory 扱いにする前の数字が残っていたもので、正しくは 5 本だった。

指標を作る記事で数字を間違えるのは、わりと格好がつかない。

検出器が自分を撃った話もある。英語版の文体スキルを lint にかけたら 5 件出て、原因は警告している悪いパターンを表に **引用している** ことで、`utilize / leverage / facilitate` と書いてある行がそのまま検出されていた。

表のセルは参照材料であって文章ではないので、lint 側で table cell を除外した (5 件 → 2 件)。

この記事自身も同じ理由で何件か出るのだけど、例を削って lint を通すのは記事が警告している失敗そのものなので、そのまま出している。

件数ではなく位置を読む案件である。

同じ罠は 3 回踏んだ。`と思う` が実測の 3 倍出ていると思って削りかけたら、半分は「文末は〜と思う」というパターン自体の引用で、著者の文か引用かを分けて数えないと自分の書き方を自分で誤認することになる。

3 回目はこの記事を書いている最中で、本文に `<p>` と書いたせいで HTML/markdown 判定が誤爆し、markdown 全体を HTML としてパースした結果「散文 307 字・1 段落」という値が出た。

つまり自分の書いたものを lint にかけると、引用と本文の区別のところから先に崩れる。

表は除外で片付いたが、本文中に引用を埋めた場合は今も区別できていない。
